## 一、目标与判断

当前产品已经具备作品浏览、单图发布、搜索（作品与用户）、分类、排行榜、点赞、收藏、评论、个人主页、账号中心、作品编辑与撤回、关注/粉丝、关注动态流、通知中心、屏蔽与拉黑、摄影教程、版权与隐私基础。

计划围绕三个核心闭环推进：

1. **关系闭环**：作品 → 作者 → 关注 → 关注内容流。**已完成基础闭环。**
2. **反馈闭环**：互动 → 通知 → 回访 → 再次创作。**已完成基础闭环（缺聚合与治理类通知）。**
3. **治理闭环**：举报 → 审核 → 处理 → 申诉与记录。**后端已具备，用户端与管理端界面未做，是本阶段最大缺口。**

### 2.1 本表与执行账本的职责

- 本表是长期产品需求池，记录稳定 ID、范围、优先级、依赖与暂定验收标准。
- 当前正在执行和近期验收的事项另见 [`PROJECT-STATUS.md`](./PROJECT-STATUS.md)。
- 不根据代码文件存在、提交记录或口头描述自动推断“已完成”；状态变化必须附带验收证据（2026-10-29 的证据汇总见第十五节）。
- 「部分完成」是本轮新增的状态值，只允许配合括注使用，写明「已完成部分 + 具体缺口」；不得用「部分完成」掩盖未开始的条目。
- 项目治理状态不得写入业务领域类型、数据库或 API；`PhotoStatus`、`ReportStatus` 等业务状态与本节无关。

### 2.2 状态迁移规则

主流程：`待确认 → 已确认 → 设计中 → 开发中 → 验收中 → 已完成`；`暂缓`和`取消`是旁路结果。
“阻塞”不是新的主状态，而是可叠加标志，例如“开发中 · 阻塞”，解除后仍回到原阶段。

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| 待确认 | 已记录问题或想法，并有稳定 ID | 价值、范围、非目标、依赖和初步验收标准明确 |
| 已确认 | 已决定实施，范围和验收标准获得确认 | S 可进入开发；M/L 须先拆分，L 还须形成设计记录 |
| 设计中 | 存在交互、接口、模型、迁移或权限决策 | 设计结论、风险、测试策略及必要的回滚方案明确 |
| 开发中 | 入口要求满足，依赖可用，当前切片明确 | 实现完成，适用检查通过，验收证据准备完成 |
| 验收中 | 主要实现已完成，已有可验证环境 | 条目验收标准与全局质量门禁均有证据 |
| 已完成 | 验收通过并进入目标分支或发布环境，文档同步 | 终态；发现遗漏时重新进入“已确认”并保留历史 |
| 部分完成 | 已交付可用的子集，且缺口已逐条写明 | 缺口补齐并通过验收后转“已完成” |
| 暂缓 | 主动决定暂不投入 | 记录原因、日期和恢复条件；恢复后回到待确认或已确认 |
| 取消 | 决定不再实施 | 记录原因与替代方案；重新提出时建立新决策记录 |

### 2.3 复杂度对应的治理要求

复杂度表示协调与风险范围，不等于优先级或精确工期；P0 不一定复杂，XL 也不一定优先。

| 复杂度 | 执行要求 |
|---|---|
| S | 单一目标与验收清单；可从已确认直接进入开发；至少保留一行技术说明 |
| M | 拆成 2–5 个可验收任务；写明接口或页面影响与测试计划 |
| L | 必须有设计记录、阶段里程碑、风险清单以及必要的数据迁移/回滚方案 |
| XL | 只作为 initiative；必须拆成不超过 L 的交付项，自身不得直接进入开发中 |

单人维护期间采用在制品限制：最多 1 个主要“开发中”、额外 1 个“设计中”、2 个“验收中”。例外必须在执行账本中说明原因。
