工科影展 · 开发工作日记

2026-10-26 · 「分部工程」式开发全程记录

这份日记写给「不是本人」的读者看：这个项目是怎么一步步做出来的、中间踩过什么坑、最后长成了什么样。 不追求术语精确，追求看得懂。主干在第二节，细节在后面。

一、一句话说清这是什么

工科影展是一个摄影作品分享社区——有点像 QQ 空间，但发的是照片，还带拍摄地点和拍摄心得。用户能点赞、收藏、评论，每周有排行榜，还能按分类找图、搜关键词。

第一版做成了纯前端：不需要服务器、不需要数据库、不需要注册任何云服务，所有数据存在使用者自己的浏览器里，打开网页就能用。

二、项目主干（先看这个，别被细节淹没）

整个开发分成 8 个阶段，每阶段是一个完整可交付的「分部工程」。做完一个就验证一个，验证不过不进入下一阶段。

  S1 打地基 ──→ S2 造数据层 ──→ S3 能看 ──→ S4 能发能登录
                                                 ↓
  S8 打包上线 ←── S7 学习与法律 ←── S6 搜索与榜单 ←── S5 能互动

用盖房子打比方：

阶段通俗理解技术说法
S1打地基、立承重墙、定装修风格工程脚手架 + 设计系统（颜色 / 按钮 / 弹窗等基础件）
S2埋管线、修仓库定义数据形状、造假数据库、灌满测试数据
S3装修出能逛的展厅首页、作品墙、详情页、分类页
S4装上大门和发布台登录注册、发作品、个人主页
S5装上点赞评论的互动装置点赞 / 收藏 / 评论 + 多标签页同步
S6装上导航和排行榜中文搜索 + 每周排行榜
S7建图书角和法律告示墙教程板块 + 7 个法律页面
S8竣工验收、打包上线代码分包瘦身 + 开源文档 + 部署

主干之外，两个决定了「好不好维护」的关键决定

① 数据层用「接口 + 可替换实现」 页面只认「我要一页作品」这个需求，不关心数据是浏览器给的还是服务器给的。所以第二期接真后端时，页面代码一行都不用改。
② 每阶段同一套验收 类型检查 0 错、代码检查 0 错、单元测试通过、构建成功、首屏体积不超预算、所有路由能打开。任一项不过，就不算完成。

三、逐阶段做了什么

S1 · 地基 14:39 起

搭好 Vite 7 + TypeScript + React 19 + Tailwind 4 + react-router 7 的骨架；配好 ESLint / Prettier / Vitest 三件套；设计明暗两套配色；做 15 个基础组件（按钮、输入框、弹窗、标签页等）+ 6 个布局组件；搭 3 个页面（首页骨架、404、组件画廊）。

值得记的一条规矩：这阶段立了「依赖方向铁律」（项目代号 FL-2），并用 ESLint 强制检查——页面可以调用数据层，但数据层不许反向引用页面。这条规矩在 S8 分包时救了命。
验收：类型检查 0 错 · 代码检查 0 错 0 警 · 构建成功 · 首屏 132.6 KB · 单测 2 个通过

S2 · 数据层 这一天最「重」的一段

定义清楚「一个作品有哪些字段」「一个用户有哪些字段」（13 个枚举、9 类实体）；写周榜公式 得分 = 1×点赞 + 3×收藏 并单独测了 6 个用例（自己给自己点赞不算数、时间区间左闭右开、名次不能重复）；写全套数据校验规则（用户名多长、密码多复杂、EXIF 哪些字段允许留）；定义 9 个「仓库接口」；用浏览器自带 IndexedDB 造一个假数据库实现这 9 个接口；灌入演示数据——10 个用户、80 张作品、300 条互动、12 篇文章，而且是幂等的，重复刷新不会灌第二遍。

为什么要造这么多数据：演示版没有真用户，只有 3 张图看不出互联网产品的样子。80 张作品能让作品墙、排行榜、搜索都显得真实。
验收：单测 8 个通过 · 首屏 137.2 KB

S3 · 能看了

时间工具（算 ISO 周、算「3 小时前」，时区锁 Asia/Shanghai）；三个数据读取钩子（无限滚动、读分类榜单、读登录状态）；作品卡片 / 缩略图 / 网格 + 无限滚动；5 个页面：首页（精选 + 榜单 Top5 + 教程 + 分类入口）、作品墙（网格 / 瀑布流切换）、详情页（大图 + EXIF + 相关推荐）、分类总览、分类墙。

一个巧妙的选择：演示版没有真实图片，所有缩略图是前端按作品 ID 生成的纯色块。好处是仓库里不含任何第三方图片，完全规避版权风险。
验收：6 条路由全部 HTTP 200 · 首屏 147.4 KB

S4 · 能登录、能发布

登录 / 注册表单（演示账号一键填入、协议必须勾选）；路由守卫（没登录访问发布页跳去登录，登录完自动跳回来）；图片处理管线——只收 JPG、自动压成 WebP 存两档（展示 2400px / 缩略 640px）、提取 EXIF 但只留 7 个白名单字段、GPS 坐标一律剔除；4 个页面：登录、注册、发布（草稿自动保存）、个人主页（三 Tab）、设置页。

为什么要抠 EXIF：手机拍的照片默认带 GPS 精确坐标。原样展示等于把用户家庭住址公开——这是摄影社区最容易出的隐私事故，所以在 S4 就堵死。
验收：9 条路由 200 · 首屏 153.1 KB · 依赖方向检查通过

S5 · 能互动了

点赞 / 收藏按钮（未登录点击跳登录）；评论区（需登录、一级回复、删除后显示占位、纯文本渲染防 XSS）；乐观更新——点一下立刻变化不用等，请求失败自动回滚；跨标签页同步——用 BroadcastChannel，一个标签页点赞，另一个标签页计数跟着变。

「乐观更新」打个比方：好比发微信，消息立刻显示在屏幕上（其实还在上传）。体验上「秒回」，技术上失败了再撤回。
验收：首屏 155.8 KB · 路由与模块 200

S6 · 能搜、有排行榜

引入 MiniSearch 做搜索，中文分词是关键难点——英文按空格分词就行，中文没有空格。方案是先用浏览器原生 Intl.Segmenter 分词，不行再用「两字一组」兜底。搜索页把关键词写在网址里（/search?q=星空，方便分享）、结果高亮、无结果有空态。周榜页有当期实时榜 + 历史终榜 + 规则公开说明。

为什么规则要公开：排行榜算法不透明，用户会怀疑暗箱操作。所以把 1×赞 + 3×藏 直接印在页面上，不藏。
验收：首屏 164.5 KB；出现「chunk 超过 500KB」警告（MiniSearch 偏大），这个警告在 S8 被彻底解决

S7 · 学习板块 + 法律页

引入 marked + DOMPurify 渲染教程 Markdown。教程含学习首页（4 大主题）、主题筛选、文章阅读（带目录锚点）；7 个法律页面：关于、服务条款、隐私政策、版权声明、DMCA、开源许可、社区规范，条款里写清授权 8 种选择与 EXIF 隐私说明。

为什么 DOMPurify 是必须的：Markdown 能内嵌 HTML，不净化就等于给 XSS 开后门。白名单标签、白名单属性、外链强制 noopener。
验收：首屏 195.1 KB —— 逼近 200 KB 预算，红线在望

S8 · 竣工验收 + 上线准备

① 分包瘦身：所有二级页面改成按需加载（React.lazy）；② 开源文档 5 件套（LICENSE / README / CREDITS / CONTRIBUTING / SECURITY）；③ 部署准备：构建后脚本自动生成 404.html 作为深链回退。

效果最戏剧性的一步：首屏从 195.1 KB 降到 126.9 KB，体积砍掉 35%。
验收：全部 24 条路由 HTTP 200 · 首屏 126.9 KB ✅ · 此时未做任何 git 操作，代码只在本机

四、最后交付时又发生了什么（S9 · 上线）

静态开发完成于 16:13。之后在 17 点前后做了三件事：换包装、开源、上线。

4.1 把长篇总结改成好读的样子

原本的《分布工程总结》是 93 行纯文字 Markdown，全是长段落。改成了两个版本：

阅读版 .html一页总览：顶部 5 个大数字卡片、一张 8 行表格、所有地址变成可点链接、跟随系统自动明暗配色
维护版 .md开头一张总览表，每阶段压缩到 2–3 个要点，长度减半

4.2 开源到 GitHub

创建 Public 仓库 lst，推上 130 个文件，配 MIT 协议、10 个话题标签。过程中踩了三个坑：

坑 1 · git 根本连不上

git push 超时 / SEC_E_NO_CREDENTIALS (0x8009030e)

逐个探测端口发现：github.com:443 通不了，只有 api.github.com 通；系统 TLS 也坏了。解法：放弃 git，全程用 GitHub REST API 建库和提交。

坑 2 · LICENSE 被认成「其他」

GitHub 显示 NOASSERTION 而不是 MIT

查 API 看到 spdx_id: NOASSERTION。原因是我在标准 MIT 文本末尾加了中文说明，破坏了指纹匹配。解法：LICENSE 恢复纯 MIT 文本，分层说明移到新建的 NOTICE.md。

坑 3 · 空仓库不能直接建树

409 Git Repository is empty

解法：先用 Contents API 打一个占位文件造出首个提交，再用 Git Data API 整体覆盖，最后用「孤儿提交」把历史压成 1 条。

一个额外的发现：写 .github/workflows/ 下的文件时，Contents API 和 Git Data API 都返回 404；但同一个 token 写 .github/test.md 却成功（201）。说明不是权限通用问题，而是 workflows 子路径单独要求 workflow scope，而这个 token 只有 repo。

4.3 部署上线

原本计划用 GitHub Actions 自动构建，因为上面那个 scope 限制，改用分支部署：

本地构建 (VITE_BASE=/lst/) ──→ 产物推到 gh-pages 分支 ──→ Pages 源设为该分支

结果：线上地址已可访问，首页 200，JS / CSS 资源全部 200，深链接有 404.html 回退。

小插曲 · 验证时自己吓自己

误报：所有资源 404

原因是我把路径拼错了——base 里已经含 /lst，验证脚本又拼了一次。改正后确认全部正常。教训：验证脚本本身也要验证。

九、一句话总结

用一天时间，从零做出一个能上线的摄影社区前端：8 个阶段、7,425 行代码、24 条路由、首屏 127 KB，代码开源、网站可访问。

关键不在「做了多少功能」，而在每一层都留了后路——数据层可以换、页面可以拆、隐私可以兜、版权可以避。这样它不只是一个演示，而是一个能继续长下去的东西。
