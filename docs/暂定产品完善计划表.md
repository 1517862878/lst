# 工科影展 · 暂定产品完善计划表

> 状态：讨论稿，不代表全部功能已经确定实施  
> 制定日期：2026-10-27  
> 对标范围：Facebook、Instagram、TikTok；Flickr、500px、Behance  
> 原则：先补运营安全线，再完成社区闭环，最后建设摄影专业差异化；商业化后置。

## 一、目标与判断

当前产品已经具备作品浏览、单图发布、搜索、分类、排行榜、点赞、收藏、评论、个人主页、摄影教程、版权与隐私基础，但仍更接近“摄影作品展示站 + 基础互动”。

计划围绕三个核心闭环推进：

1. **关系闭环**：作品 → 作者 → 关注 → 关注内容流。
2. **反馈闭环**：互动 → 通知 → 回访 → 再次创作。
3. **治理闭环**：举报 → 审核 → 处理 → 申诉与记录。

## 二、状态和复杂度定义

| 字段 | 说明 |
|---|---|
| 状态 | 待确认、已确认、设计中、开发中、验收中、已完成、暂缓、取消 |
| P0 | 公开运营前必须完成，涉及安全、治理、用户控制或明确缺陷 |
| P1 | 建立社区关系和留存闭环 |
| P2 | 建立摄影专业差异化 |
| P3 | 商业化与规模化验证 |
| 复杂度 S | 约 1 个小迭代，可单模块完成 |
| 复杂度 M | 约 1–2 个迭代，涉及前后端或多页面 |
| 复杂度 L | 约 2–4 个迭代，涉及新数据模型、运营和完整工作流 |
| 复杂度 XL | 跨多个系统，需要长期运营与风控支持 |

### 2.1 本表与执行账本的职责

- 本表是长期产品需求池，记录稳定 ID、范围、优先级、依赖与暂定验收标准。
- 当前正在执行和近期验收的事项另见 [`PROJECT-STATUS.md`](./PROJECT-STATUS.md)。
- 不根据代码文件存在、提交记录或口头描述自动推断“已完成”；状态变化必须附带验收证据。
- 项目治理状态不得写入业务领域类型、数据库或 API；`PhotoStatus`、`ReportStatus` 等业务状态与本节无关。

### 2.2 状态迁移规则

主流程：`待确认 → 已确认 → 设计中 → 开发中 → 验收中 → 已完成`；`暂缓`和`取消`是旁路结果。
“阻塞”不是新的主状态，而是可叠加标志，例如“开发中 · 阻塞”，解除后仍回到原阶段。

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| 待确认 | 已记录问题或想法，并有稳定 ID | 价值、范围、非目标、依赖和初步验收标准明确 |
| 已确认 | 已决定实施，范围和验收标准获得确认 | S 可进入开发；M/L 须先拆分，L 还须形成设计记录 |
| 设计中 | 存在交互、接口、模型、迁移或权限决策 | 设计结论、风险、测试策略及必要的回滚方案明确 |
| 开发中 | 入口要求满足，依赖可用，当前切片明确 | 实现完成，适用检查通过，验收证据准备完成 |
| 验收中 | 主要实现已完成，已有可验证环境 | 条目验收标准与全局质量门禁均有证据 |
| 已完成 | 验收通过并进入目标分支或发布环境，文档同步 | 终态；发现遗漏时重新进入“已确认”并保留历史 |
| 暂缓 | 主动决定暂不投入 | 记录原因、日期和恢复条件；恢复后回到待确认或已确认 |
| 取消 | 决定不再实施 | 记录原因与替代方案；重新提出时建立新决策记录 |

### 2.3 复杂度对应的治理要求

复杂度表示协调与风险范围，不等于优先级或精确工期；P0 不一定复杂，XL 也不一定优先。

| 复杂度 | 执行要求 |
|---|---|
| S | 单一目标与验收清单；可从已确认直接进入开发；至少保留一行技术说明 |
| M | 拆成 2–5 个可验收任务；写明接口或页面影响与测试计划 |
| L | 必须有设计记录、阶段里程碑、风险清单以及必要的数据迁移/回滚方案 |
| XL | 只作为 initiative；必须拆成不超过 L 的交付项，自身不得直接进入开发中 |

单人维护期间采用在制品限制：最多 1 个主要“开发中”、额外 1 个“设计中”、2 个“验收中”。例外必须在执行账本中说明原因。

### 3.1 阶段状态依赖与判断

- 阶段 0 是阶段 1 产品闭环的前置：先修复许可、作品写路径、隐私边界与关键限流，再扩大公开运营。
- 阶段 1 可复用现有治理数据库/API 并行建设 UI，但不能因底层存在而标记举报或审核条目完成。
- 阶段 2 的关注、屏蔽、Feed 和通知需共同定义事件、可见性、幂等与隐私规则；阶段 0/1 验收前不进入大规模开发。
- 阶段 3 只允许不延迟治理闭环的预研；商业化继续依赖可观测数据与运营承载能力。

## 十四、当前推荐决策

当前不再把 M0/M1 视为等待整体批准的全新范围；两者已有不同程度实现，应按缺口收口并验收：

1. **先收口 M0 契约和发布阻断项。** 统一五种许可；优先验证并修复 API 启动/类型检查和迁移校验；补齐 API 模式作品编辑与软撤回，不把客户端或 mock 方法当成生产能力。
2. **把隐私承诺落实到信任边界。** 服务端和数据库强制 EXIF 白名单；`hidden` 不返回地点，`city/district` 不泄露原始精确坐标；补齐发布、评论、点赞、收藏等关键写限流。
3. **并行完成 M1 产品界面。** 复用现有举报、队列、审核动作、处罚与审计 API，建设作品/评论/用户举报入口和最小审核后台；不要重复设计已落库状态，也不要标记为已完成。
4. **将举报反馈和申诉单独设计。** 当前后端具备处理和处罚基础，但没有举报者查询、处罚送达和申诉闭环。
5. **低风险传播能力可独立交付。** 同作者作品和分享/复制链接可作为小切片；逐作品 OG 只有在爬虫可访问的服务端渲染或预渲染路径完成后才可验收。
6. **M2 只进入整体设计。** 关注、屏蔽、Feed 和通知共同定义事件、可见性、幂等与隐私；M0/M1 验收前不大规模开发。
7. **M3 只做低成本预研。** 优先多图模型/存储事务、EXIF/器材公开规则和编辑制每周主题；不得延迟治理闭环。
8. **商业化继续暂缓。** 未达到另行批准的活跃、留存、治理、客服、版权和需求门槛前，不启动商业功能。
